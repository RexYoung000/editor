# Forge 权限与责任矩阵

Forge 没有应用内账号、会话、角色表、数据库或 RLS。权限依赖本机 OS、公司网络、GitHub/SVN 外部账号和人工审核；因此本表同时区分代码硬约束与协作流程约束。

## 角色

| 角色 | 责任 |
| --- | --- |
| 老师 | 编辑本机课程、确认真实预览、在 TortoiseSVN 窗口决定是否提交 |
| 课程 Agent | 仅限待评审 #161：按老师要求制作 AI 草稿并给出校验/预览，不代替老师审核 |
| 开发者 | 领取 Issue、修改功能分支、测试、推送 PR，不直接修改 `main` |
| 维护者/评审者 | 管理范围、审核 PR、维护 Project 与文档，确认合并条件 |
| 发布负责人 | 创建版本 Issue/PR、Tag、Release 和 Windows 安装包 |
| 部署负责人 | 备份部署机数据、切换正式 Tag、启动服务、验证和回退 |
| 局域网客户端 | 可以访问 Vite 页面和没有登录保护的开发 API，仅允许存在于受控网络 |

## 代码硬约束

- Electron renderer 开启 `contextIsolation`，通过 preload 暴露受控 API，不启用 Node integration。
- 文件、ZIP、URL 和库路径必须解析到允许的根目录，拒绝绝对路径、父目录跳转、UNC、空字节和越界符号链接。
- 课程另存、预览上传和发布同步在删除或覆盖前完成目标身份与目录关系检查。
- 预览确认绑定课程内容、完整工程、编辑器版本和运行环境指纹；变化后自动失效。
- 远程 SVN commit 只通过 TortoiseSVN 人工窗口；Forge 不读取或保存账号密码。
- 待评审 MCP 不公开审核、SVN、发布或部署工具，写入必须持有同一能力修订和草稿租约。

## 流程约束

- GitHub Free 私有仓库当前没有平台级 Branch Protection，禁止直接推送 `main` 主要依赖 `CONTRIBUTING.md` 和评审纪律。
- Project #1 决定任务是否可领取；Issue 决定范围与验收；PR 决定交付。三者不能互相替代。
- 最终产品发布和公司部署必须由明确负责人执行，AI 和普通功能开发者不自行完成。
- Vite API 没有身份认证。部署到公网会绕过“公司网络内使用”的核心假设，是阻塞性风险。

## 接手时需要变更的外部权限

1. 为新负责人添加 GitHub 私有仓库和 Project 权限。
2. 通过 PR 更新 `.github/CODEOWNERS`，避免所有评审继续只指向离任负责人。
3. 明确 Release、Actions workflow、公司台式机、SVN、打包机和素材快照的操作人。
4. 通过公司安全渠道交接账号和凭据；仓库只记录变量名、责任人和轮换方式。
