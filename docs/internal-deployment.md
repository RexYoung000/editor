# 正式发板与内部部署

本文定义 forge 从准备版本、生成 Windows 安装包、创建 GitHub Release，到公司台式机部署、老师端交付、后续更新和回退的完整流程。

本文面向 Rex、参与发布的开发者和执行部署的 AI。版本号与 Tag 规则见 [版本管理与发布](./versioning.md)，打包故障排查见 [Electron 打包](./electron-packaging.md)，各类验证要求见 [测试与验收](./testing.md)。

## 1. 发布模型

一次正式发板包含四项彼此关联、但分开管理的内容：

| 内容 | 作用 | 版本来源 | 分发方式 |
| --- | --- | --- | --- |
| 源代码 | 公司台式机运行编辑器页面、预览和 API | Git Tag `vX.Y.Z` | 私有 GitHub 仓库；Release 自动生成源码归档 |
| Windows 安装包 | 老师电脑上的 Electron 客户端、本地文件和编译能力 | 同一版本的 `package.json` | 手动上传到 GitHub Release，并单独发给老师 |
| 美术资源库 | 资源库浏览、搜索和下载 | Release 记录的素材快照标识 | 单独同步到公司台式机，不进入 Git 仓库或安装包 |
| 运行数据与本机配置 | 上传内容、预览课件、服务地址和环境配置 | 不随应用版本变化 | 保留在原设备，更新前单独备份 |

正式版本以已经发布的 GitHub Release 为准。Tag 是不可变的代码定位点，Release 是面向交付的版本页面；只有 Tag、安装包、发布说明和必要素材信息都齐全后，才可以对外宣布版本可用。

公司台式机必须运行某个已发布 Release 对应的 Tag，不得长期跟随 `main`、发布分支或任意提交。老师端安装包原则上与服务器使用同一个版本配套交付。

## 2. 目录与数据边界

更新代码前必须区分 Git 管理内容和设备本地内容：

| 路径或内容 | 是否随 Git 分发 | 更新要求 |
| --- | --- | --- |
| 仓库已跟踪文件 | 是 | 由目标 Tag 决定，不在部署机直接修改 |
| `public/builtin/library/` | 否 | 使用发布说明指定的素材快照单独同步 |
| `public/uploads/` | 否 | 视为运行数据，更新前备份并保留 |
| `preview-server/lessons/` | 否 | 视为预览产物，更新前备份；不得用 Git 清理 |
| 用户课程、自定义模板和正式发布产物 | 否 | 保存在用户选择的目录，更新不得覆盖 |
| 服务环境变量、凭据、证书和启动配置 | 否 | 保存在仓库外或 Git 忽略位置，不提交真实值 |
| Electron 保存的服务器地址 | 否 | 位于老师电脑的应用数据目录，升级安装时应保留 |

禁止在部署机使用 `git clean` 清理仓库，也不得用 `git reset --hard` 处理来源不明的改动。发现已跟踪文件被本地修改时，应停止更新，先确认修改来源和是否已经进入正式版本。

### 2.1 素材快照

美术资源库不进入 Git，因此每次 Release 必须使用一个不会被覆盖复用的素材快照标识。首次可以采用 `library-YYYYMMDD-r1`，同日修订递增末尾序号；已有正式命名体系时沿用已有规则。

素材快照应满足：

- Release 记录快照标识；未变化时明确记录沿用的上一版本快照。
- 同一标识的内容发布后不再原地替换，修订内容使用新标识。
- 部署前确认来源完整，部署后抽查目录浏览、搜索和实际下载。
- 至少保留当前版本和上一可回退版本使用的快照。
- `public/builtin/library/.cache/` 是服务生成缓存，不作为素材源文件或快照依据。

素材快照的真实存储地址、访问凭据和公司网络信息保存在仓库外；GitHub Release 与版本 Issue 只记录不敏感的快照标识和验收结果。

## 3. 版本准备

### 3.1 创建版本任务

准备向老师交付一组变化时：

1. 创建版本 Issue，记录目标版本、纳入的 PR、用户变化、回归范围、已知风险和预期回退版本。
2. 从最新 `main` 创建 `release/<version>` 分支和发布 PR。
3. 按 [版本管理与发布](./versioning.md) 选择 PATCH、MINOR 或 MAJOR。
4. 在发布 PR 中更新 `package.json` 的 `version` 和 README 展示版本。
5. 普通功能 PR 不提前修改版本号，避免并行分支产生版本冲突。

### 3.2 确认交付组合

版本 Issue 必须在打包前确认：

- 目标服务器版本和目标 Windows 安装包版本一致。
- 本次素材库使用哪个快照；未变化时明确写“沿用上一版本素材”。
- 老师是否必须重新安装客户端。
- 本次是否包含数据、课程格式、工程结构或使用方式的不兼容变化。
- 上一可用 Release 和回退所需的安装包、素材快照是否仍可取得。

### 3.3 客户端升级判断

出现以下任一变化时，Release 必须标记“需要重新安装客户端”：

- `electron/` 下的主进程、preload、本地文件或 IPC 行为变化。
- Electron、打包工具、本地编译工具或 Windows 运行依赖变化。
- `package.json` 的 Electron 打包配置或 `extraResources` 变化。
- 服务器页面依赖了旧客户端不存在的新本地能力。
- 无法确认新服务器与旧客户端兼容。

只有发布评审明确确认变更完全位于服务器侧，且没有新增或改变本地能力时，才可以标记“客户端无需升级”。在建立自动兼容检查前，不确定时默认要求升级。

## 4. 发布前验证与 Windows 打包

### 4.1 自动检查

在发布分支执行：

```bash
pnpm install --frozen-lockfile
pnpm lint
pnpm test
pnpm build
```

检查必须全部通过。`pnpm build` 只验证静态 SPA 构建，不能替代 Vite API、Electron、本地文件、预览和发布链路验收。

### 4.2 版本人工回归

至少完成以下真实环境检查：

1. 在公司部署方式等价的 Vite 服务上连接 Electron。
2. 打开、编辑、保存并重新打开一份真实课程。
3. 浏览资源库并下载至少一种本版本涉及的素材。
4. 完成至少一种正常课件的预览和发布。
5. 回归本版本涉及的课程类型、组件、资源和异常场景。
6. 确认编辑器显示版本与 `package.json` 一致。
7. 记录未覆盖环境、已知问题和回退方式。

### 4.3 生成安装包

最终 Windows 安装包在 Windows 环境执行：

```bash
pnpm electron:build
```

当前安装包输出到：

```text
release/<version>/豌豆课件编辑器 Setup <version>.exe
```

不能只验证 `win-unpacked`。必须实际安装 NSIS 安装包，并检查：

- 首次安装和从上一正式版本覆盖安装。
- 启动、服务器地址输入与地址保留。
- 服务器连接失败时能够识别问题。
- 本版本涉及的本地文件、模板、资源复制、编译和发布 IPC。
- Windows Defender 或普通权限环境下的关键流程。
- 关闭和重新启动后功能仍然正常。

为最终安装包生成 SHA-256，并将校验值写入 Release 说明。PowerShell 示例：

```powershell
Get-FileHash ".\release\1.2.0\豌豆课件编辑器 Setup 1.2.0.exe" -Algorithm SHA256
```

## 5. 创建 Tag 与 GitHub Release

发布 PR 通过评审并 Squash 合并后，在 `main` 的合并提交创建带注释 Tag：

```bash
git switch main
git pull --ff-only origin main
git tag -a v1.2.0 -m "发布 1.2.0"
git push origin v1.2.0
```

Tag 必须满足：

- 指向发布 PR 合并后的提交。
- 版本号与 `package.json`、README 和安装包名称一致。
- 不移动、不覆盖已经发布的同名 Tag；发现错误时发布新的修复版本。

然后创建 GitHub Release。GitHub 会根据 Tag 自动提供 Source code ZIP 和 TAR.GZ，不需要人工再次上传源码。需要人工上传 Windows 安装包，并填写以下发布说明：

```markdown
## 版本信息

- 版本：v1.2.0
- 发布日期：YYYY-MM-DD
- 服务器代码：v1.2.0
- Windows 安装包：豌豆课件编辑器 Setup 1.2.0.exe
- 客户端升级：需要重新安装 / 无需升级
- 素材库：素材快照标识 / 沿用 v1.1.0
- 回退版本：v1.1.0

## 用户可感知变化

- ...

## 修复

- ...

## 已知问题与限制

- ...

## 部署说明

- 公司台式机需要更新 / 无需更新
- 素材库需要同步 / 无变化
- 其他前置条件：...

## 安装包校验

- SHA-256：...

## 关联记录

- Version Issue：#...
- PR：#...
```

发布前从 Release 页面重新下载或核对安装包，确认文件名、大小和 SHA-256 与已验证产物一致。最终由 Rex 发布 Release、执行内部部署或明确授权具体版本的部署。

## 6. 公司台式机首次部署

### 6.1 前置条件

公司台式机需要：

- 可访问私有 GitHub 仓库的独立账号或部署凭据。
- Git、Node.js 22 LTS、Corepack 和 pnpm 10。
- 稳定的局域网地址；防火墙允许老师电脑访问 6688 端口。
- 与目标 Release 对应的素材快照。
- 仓库外的备份位置和服务启动配置。

凭据、真实 IP、证书和密码不得写进仓库文档、脚本或 Issue。

### 6.2 获取指定版本

以下命令中的版本必须来自已经发布的 GitHub Release：

```bash
git clone https://github.com/RexYoung000/editor.git
cd editor
git fetch --tags --prune origin
git switch --detach v1.2.0
corepack enable
pnpm install --frozen-lockfile
git describe --tags --exact-match
```

`git describe --tags --exact-match` 必须输出目标 Tag。部署机使用 detached HEAD 是预期行为，它表示当前精确固定在正式版本，不应在该目录直接开发或提交。

### 6.3 放置资源与配置

1. 将发布说明指定的素材快照放入 `public/builtin/library/`。
2. 确认 `preview-server/` 中由 Git 跟踪的 GameLoader 与公共资源完整。
3. 在仓库外或 Git 忽略位置配置 `WS_SERVER`、`WS_HOST` 等环境值。
4. 不恢复其他电脑的绝对路径、Token 或 Electron 用户配置。
5. 记录实际部署的 Tag、提交、素材快照、部署时间和执行人。

### 6.4 启动当前服务

当前 forge 没有独立生产后端；编辑器页面、资源库、预览路由和 `/api/*` 都由 Vite dev server 提供。因此必须运行：

```bash
pnpm dev
```

不能用 `pnpm build` 后的静态文件或 `pnpm preview` 替代，因为它们不提供 forge 所需的开发 API。

当前仓库尚未提供 Windows 服务、进程守护或自动重启脚本。人工启动时，终端关闭或进程退出都会中断老师使用；在自动托管能力正式实现前，部署负责人必须确保该进程持续运行，并在机器重启后重新启动。

### 6.5 首次部署验收

1. 在公司台式机浏览器打开 `http://localhost:6688`。
2. 在同一局域网的另一台电脑打开 `http://<公司台式机地址>:6688`。
3. 确认编辑器版本、首页和资源库可用。
4. 安装对应 Windows 客户端并填写同一服务器地址。
5. 打开真实课程，完成保存、素材下载、预览和发布抽查。
6. 重启客户端，确认服务器地址仍然保留。
7. 记录验收结果、未覆盖项和当前回退版本。

只有浏览器首页能打开，不代表 Electron、本地文件、编译和课件预览可用。

## 7. 老师端交付

交付给老师的内容至少包括：

- 已验证的 Windows 安装包，文件名与 Release 一致。
- 对应的服务器地址，不使用 `localhost` 指代公司台式机。
- 是否必须覆盖安装或卸载旧版本。
- 本版本主要变化和已知限制。
- 出现连接失败时的反馈入口和需要提供的信息。

推荐交付顺序：

1. 先完成服务器部署和内部验收。
2. 再向小范围验证老师提供安装包与服务器地址。
3. 验证真实课程工作流后，再扩大分发范围。
4. Release 标记“客户端无需升级”时，仍需通知老师重新启动客户端，使服务器页面重新加载。

老师反馈问题时，至少收集编辑器版本、Windows 版本、服务器地址、课程类型、复现步骤和截图或错误信息。课件发布后可通过课程根目录的 `editor-version.txt` 追踪生成该课件的编辑器版本。

## 8. 更新到新版本

### 8.1 更新前检查

开始前确认：

- 目标版本已经是正式 GitHub Release，不是草稿、Tag 候选或 `main` 最新提交。
- Release 已说明客户端升级、素材变化、已知风险和回退版本。
- 目标安装包和素材快照可取得。
- 当前 Tag、提交、素材快照和运行状态已经记录。
- 已跟踪文件没有来源不明的本地修改。
- `public/builtin/library/`、`public/uploads/`、`preview-server/lessons/` 和其他重要本机数据已有可恢复备份。

### 8.2 更新步骤

1. 通知验证用户并停止当前 `pnpm dev` 进程。
2. 记录当前版本：

```bash
git status --short --branch
git describe --tags --exact-match
git rev-parse HEAD
```

3. 获取并核对目标版本：

```bash
git fetch --tags --prune origin
git show --no-patch --decorate v1.2.1
```

4. 确认工作区不存在待保留的已跟踪改动后，切换 Tag 并安装锁定依赖：

```bash
git switch --detach v1.2.1
pnpm install --frozen-lockfile
git describe --tags --exact-match
```

5. 按 Release 说明同步素材快照；未变化时保留现有素材库。
6. 恢复或确认服务环境配置，启动 `pnpm dev`。
7. 按“首次部署验收”完成服务器和 Electron 冒烟检查。
8. Release 要求升级客户端时，再分发并安装对应版本；不要在服务器验收前通知老师升级。
9. 记录实际部署版本、素材快照、备份位置、验收结果和回退点。

“更新到最新版本”只能解释为更新到 GitHub 上最新的正式非草稿 Release，不能解释为拉取 `main`。更稳妥的做法是始终给出明确 Tag，例如“更新公司服务器到 `v1.2.1`”。

## 9. 回退

出现阻塞老师使用、课程损坏、编译失败或关键功能不可用时：

1. 停止当前服务，保留故障日志和复现信息。
2. 确认上一可用 Release 的 Tag、安装包和素材快照。
3. 切回上一 Tag，并按该版本 lockfile 安装依赖：

```bash
git switch --detach v1.1.0
pnpm install --frozen-lockfile
git describe --tags --exact-match
```

4. 如果新版本修改了素材库，恢复与上一版本匹配的素材快照。
5. 默认保留更新期间产生的课程、上传和预览数据；只有确认数据本身已损坏时，才从备份恢复。
6. 启动 `pnpm dev`，完成服务器和真实 Electron 验收。
7. 若客户端升级不向后兼容，向受影响老师重新分发上一版本安装包。
8. 在版本 Issue 中记录故障、影响、回退结果和后续修复计划。

不得移动已有 Tag、覆盖 Release 资产或直接在部署机修改源码制造“临时正式版”。修复应通过新的 Issue、PR 和 PATCH Release 交付。

## 10. AI 执行规则

当 AI 在公司台式机执行部署时：

1. 必须先读取本文、目标 GitHub Release 和关联版本 Issue。
2. Rex 未指定版本时，先核对最新正式 Release；不得自行选择 `main` 或预发布版本。
3. 更新前报告当前 Tag、工作区状态、目标 Tag、客户端升级要求、素材变化和回退点。
4. 发现已跟踪文件有本地修改、目标 Release 资产不完整、素材快照缺失或无法回退时，停止部署并说明阻塞。
5. 不使用 `git reset --hard`、`git clean`、强制切换或覆盖本机数据。
6. 只有 Rex 明确授权部署具体版本后，才执行停止服务、切换版本和重新启动等影响老师使用的操作。
7. 完成后必须报告实际 Tag 和提交、依赖安装结果、服务地址、素材快照、验收结果、未覆盖项、老师是否需要升级以及回退版本。

AI 可以帮助准备命令、核对 Release、执行已授权的可逆更新和验证，但不能自行发布 Release、扩大分发范围或执行未经确认的数据恢复。

## 11. 部署记录

首次部署、版本更新或回退完成后，在版本 Issue 增加一条部署记录。不要写入真实 IP、凭据或本机绝对路径；备份只记录可供负责人定位的非敏感标识。

```markdown
## 内部部署记录

- 操作：首次部署 / 更新 / 回退
- 时间：YYYY-MM-DD HH:mm
- 执行人：...
- 目标 Tag：v1.2.0
- 提交：完整 commit SHA
- 上一 Tag：v1.1.0 / 无
- 素材快照：library-YYYYMMDD-r1
- 备份标识：...
- 服务检查：本机通过 / 局域网通过
- Electron 检查：连接、课程保存、资源、预览、发布
- 客户端动作：需要升级 / 无需升级 / 已回退
- 回退点：v1.1.0 + 对应素材快照
- 未覆盖项与已知问题：...
```

部署记录描述实际结果，不复制发布计划。某项未验证时必须写“未验证”和原因，不能用“正常”概括全部链路。

## 12. 发布与部署完成标准

一次发板只有同时满足以下条件才算完成：

- 版本 Issue 与发布 PR 内容一致，自动检查和人工回归通过。
- `package.json`、README、Tag、Release 和安装包版本一致。
- Release 包含完整发布说明、Windows 安装包和 SHA-256。
- 公司台式机运行目标 Tag，素材快照和运行配置已核对。
- 服务器、Electron、资源库、真实课程保存、预览和发布完成验收。
