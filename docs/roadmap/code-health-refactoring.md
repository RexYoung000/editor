# forge 代码健康治理与渐进式重构路线

> 更新日期：2026-07-16
>
> 用途：记录代码健康基线、治理顺序、立项条件和阶段复评结果，作为后续开发者与 AI 的长期技术上下文。
>
> 关联任务：[Issue #31](https://github.com/RexYoung000/editor/issues/31) · [Issue #32](https://github.com/RexYoung000/editor/issues/32) · [Issue #33](https://github.com/RexYoung000/editor/issues/33)

## 一、当前判断

forge 当前不是需要全面重写的失控代码库。项目已有统一状态源、明确的 Electron 与远程 Vite 边界、统一组件元数据、架构和专项文档，以及 lint、TypeScript 构建和单元测试门禁，仍能稳定承载阶段性产品迭代。

当前风险主要集中在少数持续增长的核心模块：

- 正式发布与预习导出存在大量相似规则，但缺少直接覆盖最终生成结果的自动测试。
- 全局 Store 同时承载课程、页面、元素、选择、历史、模板和组合组件操作，修改半径正在扩大。
- 画布同时处理 React、Laya 生命周期、状态同步和输入交互，复杂度较高。
- 属性面板、组件工具栏和资源浏览器已经形成较大的界面模块，但尚未出现必须脱离产品主线单独重写的用户问题。

因此采用渐进式治理，不发起“重构整个项目”或“拆分所有大文件”的长期工程。治理顺序统一为：

```text
建立测试保护 → 识别真实重复与职责边界 → 小步抽离 → 验证结果一致 → 回写路线
```

## 二、2026-07-16 健康基线

本基线用于后续复评，不作为机械质量门槛。

| 观察项 | 当前结果 | 说明 |
| --- | --- | --- |
| 静态检查 | `pnpm lint` 通过 | 当前 ESLint 基线为零错误 |
| 单元测试 | 75 项通过 | 覆盖画布几何、交互事务、内部页面、导出结果、模板资源和资源库检索 |
| 类型与构建 | `pnpm build` 通过 | TypeScript 与 Vite 生产构建正常 |
| 生产 JS | 约 842 KB，gzip 约 229 KB | 当前存在超过 500 KB 的构建提醒，尚无真实性能阻塞证据 |
| 全局 Store | 约 2689 行、约 91 个操作 | 仍保持 Zustand 单一状态源，但领域职责集中 |
| 正式发布导出 | 约 2577 行 | 承载资源、场景、动作代码、配置和写盘编排 |
| 预习导出 | 约 1183 行 | 与正式发布存在大量相似资源和场景生成规则 |
| 画布主体 | `Canvas.tsx` 约 934 行 | 已开始把几何、选择和变换事务抽为可测试模块 |

文件行数和构建提醒只用于发现可能的职责集中，不能单独作为重构立项依据。

## 三、风险分级与处理策略

| 区域 | 风险 | 主要依据 | 当前策略 |
| --- | --- | --- | --- |
| 预览与发布导出 | 高 | 最终结果关键、规则重复、缺少直接输出测试 | 优先建立回归保护，再收敛共享规则 |
| 全局 Store | 中高 | 操作数量多、业务领域集中、调用范围广 | 保留单一状态源，阶段一完成后按领域复评 |
| 画布与 Laya 同步 | 中高 | 生命周期、渲染同步和输入交互集中 | 随阶段一产品 Issue 继续抽离纯逻辑和事务 |
| 属性面板与工具栏 | 中 | 组件较大、直接读取较多 Store 能力 | 随图层和组件体系任务收敛，不单独重写 |
| 资源浏览与模板文件 | 中低 | 状态和文件规则较多，但当前边界可用 | 等真实规模或失败恢复问题触发后再立项 |
| 性能与构建拆包 | 低 | 有体积警告和无效动态导入，但暂无用户阻塞 | 记录基线，出现真实性能问题后治理 |

风险等级发生变化时，应记录新的事实和影响，不能只修改结论。

## 四、不可破坏的治理约束

- 保留 `src/store/editorStore.ts` 的 Zustand Store 作为唯一全局状态源，不引入 Redux 或新的全局 Context。
- 不建立第二套组件元数据、资源注册或导出入口。
- 不改变现有课程数据、导出格式、目录结构和运行时协议，除非另有明确产品 Issue 和迁移方案。
- 不破坏“电脑 A 运行 Vite、电脑 B 运行 Electron”的远程模式。
- 共享规则抽离前先建立能保护真实结果的测试；测试不能通过降低断言强度制造通过。
- 产品 Issue 只包含实现该用户结果所必需的局部治理，不借机重写整个关联模块。
- 独立技术 Issue 必须能够单独测试、单独评审、单独合并，并明确证明用户行为或输出结果保持一致。
- 不为了减少文件行数机械拆分；拆分必须形成清晰职责、单一规则来源或更可测试的边界。

## 五、六阶段治理路线

### 阶段一：导出结果回归保护

由 [Issue #32](https://github.com/RexYoung000/editor/issues/32) 承载。

- 为正常课、作业课、专题测评、预习、复习课和内部页面建立代表性输入。
- 验证场景节点、变量、动作代码、配置和关键资源路径。
- 测试不依赖真实 Electron 写盘、SVN、未入库素材或远程服务。
- 以稳定关键结构为断言对象，避免用不可维护的整文件快照掩盖差异。

完成标准：后续导出规则调整能够在 CI 中发现关键结果变化，并提供可读差异。

2026-07-16 实施结果：新增不依赖 Electron、SVN、网络和本机素材的纯结构入口，真实写盘与测试共同使用场景、代码和配置的组合逻辑；六类代表夹具覆盖组件树、坐标转换、变量与动作、内部页面运行代码、课程类型差异，以及图片、音频、视频、Spine 和内置资源路径。完整单元测试增至 75 项。

### 阶段二：共享导出规则收敛

由 [Issue #33](https://github.com/RexYoung000/editor/issues/33) 承载，依赖 #32。

- 收敛正式发布与预习导出的资源识别、路径转换和属性重写规则。
- 收敛变量分配、包装节点和可复用场景节点构建。
- 明确保留正常课、作业、测评、预习和复习课的真实差异。
- 不调整 SVN、上传、文件写入或 GameLoader 打开流程。

完成标准：共享规则只有一个核心实现，课程类型差异有明确入口和测试，重构前后关键输出一致。

2026-07-17 实施结果：预习导出移除约 700 行平行实现，资源收集、路径重写、变量分配、包装节点、特殊组件场景节点、内置资源筛选和 zip 解压统一复用正式导出核心；预习场景代码模板、页面配置和写盘目录继续保留独立入口。新增跨正式与预习的场景结构一致性断言，并补充内置资源引用/解压路径一致性及预习正课专用反馈边界保护，完整单元测试增至 87 项。Electron 临时课件已验证正常课与预习课工程生成、拖拽组件双皮肤资源、编译上传和 GameLoader 打开。

### 阶段三：阶段一产品迭代中的伴随治理

随 #14～#20 实施，不另外创建“重构画布”总 Issue。

- 智能吸附和等间距能力优先抽离成不依赖 React 与 Laya 的计算逻辑。
- 图层数据视图、选择同步和状态继承以可测试的派生规则承载。
- 画布高频交互继续通过事务统一预览、提交、取消和历史记录。
- 每个产品 PR 说明本次新增或减少的耦合，以及未覆盖的后续治理点。

边界：只处理当前用户结果需要的部分，不扩大为 `Canvas`、`CanvasOverlay` 或 Store 全量重写。

### 阶段四：阶段一结束后的 Store 复评

触发点为 #14～#20 完成并由 #13 完成阶段一端到端回归。

复评内容：

- Store 的领域职责、操作数量、调用范围和直接测试覆盖。
- 页面、元素和组合组件操作是否继续重复查询与修改同一数据结构。
- 历史记录是否仍由不同业务操作自行拼接，导致原子提交风险。
- 新增阶段一能力后，修改一个用户行为需要同时触碰多少高风险中心。

候选治理方向：

1. 抽离关卡、页面和内部页面的领域操作。
2. 抽离元素选择、复制和历史事务。
3. 抽离翻页、选择题、填空题、连线题和拖拽题等组合组件操作。

候选方向不是预先批准的 Issue。只有复评证明它可以独立测试、独立合并且保持行为不变时才正式立项。

### 阶段五：组件界面、资源与模板治理

组件界面治理随 #21～#25 推进：

- 组件入口、工具栏和属性面板优先消费统一元数据与查询结果。
- 不让业务归属、阶段、隐藏状态或高频规则重新散落到多个界面组件。
- 阶段二结束后复评 `ElementToolbar`、`PropertyPanel` 与组件元数据之间的职责。

资源与模板仅在以下事实出现时立项：

- 相同资源识别或去重规则在不同链路产生偏差。
- 远程模式路径问题持续出现，且无法由现有边界规则解决。
- 模板保存、导入或应用失败后难以恢复，开始影响真实制作。
- 素材规模明显影响仓库、下载或多人协作。

未触发前，不因 `LibraryBrowser` 或模板文件模块较大单独重构。

### 阶段六：性能与构建治理

当前记录约 842 KB 的生产 JS 基线，以及动态导入因同时被静态引用而无法拆包的构建提醒。

只有出现以下一种真实影响时才建立性能或拆包 Issue：

- Electron 或浏览器启动时间影响日常使用。
- 核心编辑交互出现可复现的卡顿或内存问题。
- 远程加载或发布产物体积影响稳定使用。
- 构建体积持续增长且能够定位到明确功能边界。

治理以测量数据和用户影响为依据，不以消除构建警告为目标。

| 资源与模板链路治理 | 出现重复规则偏差、远程路径或失败恢复问题 | 真实使用反馈 | 数据完整、失败可恢复、远程边界不变 |
| 构建拆包与加载优化 | 有可测量的启动、加载或体积问题 | 性能基线对比 | 指标改善且不破坏 Electron 与远程模式 |

### 暂不处理

- 全面更换 Zustand、React、LayaAir 或 Electron 架构。
- 一次性重写 `editorStore.ts`、`Canvas.tsx` 或整个导出系统。
- 仅为了降低文件行数进行目录或文件拆分。
- 在没有真实性能问题前，为消除构建警告重组所有 import。
- 在组件盘点和高频结构尚未明确前，提前重建模板或资源体系。

## 七、复评与维护机制

以下情况必须复评本路线：

1. 任一阶段 Milestone 完成。
2. 核心模块发生大规模功能变化或新增一种课程、页面、组件运行模式。
3. 同一规则在多个链路出现可复现偏差。
4. 一个普通功能需要同时修改三个及以上高风险中心。
5. 自动检查持续无法覆盖实际出现的回归。

每次复评至少更新：

- 风险等级和新的事实依据。
- 自动测试、真实验收和未覆盖范围。
- 重复实现与单一规则来源的变化。
- 已完成治理项的实际结果。
- 候选项是否达到正式立项条件。
- 已失效、已被替代或决定暂不处理的建议。

产品 Issue 中完成必要的局部抽离时，在对应 PR 记录结果；如果它改变了本路线的风险、任务或触发条件，再同步更新本文档。不要为同一结果重复创建技术 Issue。

## 八、持续观察指标

- 核心输出是否具备自动回归测试。
- 同一业务规则是否存在多套实现，并可能产生偏差。
- 一个用户结果需要修改多少高风险中心。
- 领域逻辑是否可以脱离 React、Laya、Electron 或真实文件系统单独测试。
- 历史、保存、预览和发布是否仍使用一致的数据来源。
- 重构前后真实体验和导出结果是否保持一致。

这些指标用于帮助判断，不设置固定行数、文件数量或覆盖率门槛。正式立项仍需说明具体问题、影响、边界、依赖和验收方式。
