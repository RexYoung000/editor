# 事件与动作系统

本文定义 forge 中触发元素、判定目标、结果分支和导出运行时之间的长期边界。具体 sdk_baiya 组件能力见 [SDK 组件参考](./sdk-baiya-components.md)，生成代码见 [导出流程](./export-pipeline.md)。

## 一、角色由事件关系决定

元素创建时没有固定的“触发者”或“被判定者”身份。同一个元素可以在一条事件中触发动作，也可以在另一条事件中成为目标。

- **触发元素**：保存事件和结果动作，回答“什么时候执行、判定谁、得到结果后做什么”。
- **判定目标**：保存答案和题型规则，回答“什么状态算正确、错误或未完成”。
- **事件关系**：由触发元素上的 `Action.event` 和 `Action.judgeTargetId` 建立，不通过元素类型或图层位置猜测。

点击触发的 SDK 判定事件必须保存在触发元素上。输入完成、选项变化或连线变化后的自动判定仍可保存在题型组件自身，两者是不同入口，不互相替代。

### 普通事件的课程一致性

`onClick`、`onClickSound`、`onLoad` 和 `onChange` 属于普通元素事件。只要课件类型会生成可编辑场景，正课、预习、作业和专题测评都必须使用同一套普通事件编译规则；课程类型只能追加自己的判定、翻页或内部页面能力，不能遗漏普通事件监听。复习课保持纯视频结构，不生成普通事件场景。

同一触发元素的同一普通事件只绑定一次，并按编辑器动作顺序执行该事件下的有效动作。`onClickSound` 每次触发先播放一次内置点击音效，再执行全部动作；不得因一个事件包含多个动作而重复播放点击音效。内部页面动作、SDK 判定、翻页和其他专项事件继续由各自编译入口负责，普通事件编译不得再次绑定。

## 二、基础控件、判定关系与题型模板

题型能力由三层组成，不能把快捷题型组件当作唯一配置入口：

- **基础控件**保存自身答案或正确关系，并暴露当前作答状态。独立输入格等原子控件也可以成为判定目标。
- **判定关系**连接触发元素与判定目标，并保存正确、错误、未完成后的结果动作。
- **题型模板**一次创建基础控件、触发元素、反馈元素和预设关系，用于快速搭建；模板创建后的每个部分仍可独立编辑和替换。

“被判定”不是目标组件自身的一种触发事件。目标组件只显示自身判定设置和入站引用；点击等事件仍保存在触发元素上，避免一个目标被多个触发者引用时产生关系归属冲突。

## 三、SDK 通用判定

“点击 + SDK 通用判断”允许任何能够配置点击事件的元素作为触发者，但目标选择器只显示当前页面中具备真实 SDK 判定能力的组件。

| 判定目标 | 答案或规则来源 | 运行时判定 | 结果能力 |
| --- | --- | --- | --- |
| `KlInputImage` | 目标组件编辑器属性 `_judgeAnswer` | `fontClipValue` 与答案比较 / `valueOrSkinIsNull` | 正确、错误、未完成 |
| `KlInputBox` | 目标组件 `answer` | `isRight()` / `isNull()` | 正确、错误、未完成 |
| `ChoiceBox` | 目标组件 `_correctOptionIds`，导出时转换为选项名集合 | `isRight` / `isNull` | 正确、错误、未完成 |
| `DragViewBox` | 子级拖拽对象与放置区关系 | `dragsOnRightDrops()` | 正确、错误 |
| `MatchingGame` | 子级连线项的正确连接关系 | `allRight` / `isNull()` | 正确、错误、未完成 |

`KlInputImage` 没有 SDK 容器式 `isRight()`，但 SDK 已提供 `fontClipValue` 和 `valueOrSkinIsNull`。编辑器使用 `_judgeAnswer` 保存答案，导出时生成等值判断，不把 `_judgeAnswer` 写入运行时 scene。普通图片、文本、图层组和没有作答状态的组件不能作为 SDK 判定目标；判断它们的 `visible`、`selected` 或自定义属性属于另一套“属性条件判断”能力，不在 SDK 通用判定中隐式支持。

## 四、编辑器交互

选中触发元素时，右侧事件区域按以下顺序配置：

1. 选择点击事件及“SDK 通用判断”能力。
2. 从当前页面兼容目标中选择一个判定目标。
3. 显示目标类型、答案或关系摘要；答案仍写入目标组件，不复制到事件数据。
4. 按目标真实能力显示正确、错误和可选的未完成分支。
5. 每个结果分支继续复用现有显示、音效、动画、锁屏和页面动作。

选中独立 `KlInputImage` 时，右侧直接显示“正确答案”；修改答案不会创建额外容器。新增 SDK 判定关系时，按目标能力自动建立正确、错误、未完成分支，并预填 SDK 通用正确与错误反馈，用户可以替换或删除各分支动作。

“播放 SDK 通用胜利动画 / 失败动画”和两个“SDK 默认反馈（兼容）”动作只负责调用 SDK 反馈能力。默认 `feedback: spirit` 下，豌豆精灵动画及其胜利、失败、未完成音效由当前实际加载的 SDK 运行时统一提供；导出器不得再附加 `playRightSound` / `playWrongSound`，避免同一次反馈播放两遍音效。只有老师显式配置独立音效动作时，才生成额外音效调用。

目标缺失、类型不再兼容或不在当前页面时，右侧必须显示失效关系，导出不得静默生成错误引用。选中判定目标时，应显示它被哪些 SDK 判定事件引用，帮助用户理解关系来源。

事件区域中的判定目标、动作目标、兼容判定目标、画笔目标和入站引用统一显示当前图层名称，并在已有位置保留组件类型说明。老师修改图层名称后，这些入口必须立即显示新名称；关系绑定继续使用稳定元素 ID，不因改名而重建或丢失。`targetNameSnapshot` 和 `judgeTargetNameSnapshot` 只用于目标已删除或不再兼容时的断链提示，不能覆盖仍然存在的目标名称。

快捷填空题、选择题、拖拽题和连线题继续自动创建确认按钮、反馈元素与预设事件，但它们属于题型模板，只是创建效率工具，不是唯一入口。

## 五、数据与兼容

- 新的点击判定关系继续使用触发元素的 `actions`，通过独立的 `judgeTargetId` 引用判定目标。
- `targetId` 继续表示结果动作要操作的元素；判定目标和动作目标不能复用同一字段，否则结果分支无法操作其他图层。
- 结果动作继续使用 `branchId` 和 `branchCondition`；不为每种题型建立平行数据结构。
- 目标名称快照只用于目标失效后的提示，不能代替真实 `targetId`。
- 历史 `onClickInitConfirm*`、`onClickInitGameConfirm*`、`onInputJudge`、`onChoiceJudge`、`onDragJudge` 和 `onMatchingJudge` 保持读取、编辑和导出兼容。
- 历史确认事件的 `targetId` 仍使用稳定元素 ID；删除目标后保留断链，但属性面板必须显示失效目标，预览和发布必须阻止继续，不能按图层名称或下拉框首项静默重绑。
- 新入口不得重写 sdk_baiya 的答案算法，只在导出层根据目标类型调用现有方法。
- 独立 `KlInputImage` 是例外：SDK 已提供输入值和空值状态但没有 `isRight()`，导出层只补充“当前值与编辑器答案相等”的基础比较。

## 六、当前范围

Issue #60 只实现单个 SDK 判定目标，包括独立 `KlInputImage`。Issue #83 进一步明确作业运行时预设“完成”的特殊入口：它不是画布上的触发元素，因此不要求作者额外建立点击判定关系；独立 `KlInputImage` 或 `FractionInput` 只要配置了非空 `_judgeAnswer`，就自动参与作业页结果判定。

作业预设完成遵循以下规则：

- 只自动收集不属于答题判定容器、且 `_judgeAnswer` 非空的 `KlInputImage` 与 `FractionInput`；快捷填空题继续由 `KlInputBox` 负责，显式开启答题判定的 `ContainerBox` 同样由父容器统一负责。
- 任一参与判定的输入控件未填写时，页面结果为未作答；全部填写且全部匹配时为正确；全部填写但任一不匹配时为错误。
- 未配置答案的输入控件仍是普通输入，不参与判定。
- 显式 `onClickSdkJudge` 关系继续可用；自动完成判定只读取控件状态，不重复执行关系中的反馈动作。

以下内容仍不在当前范围：

- 普通元素属性条件判断。
- 任意题型之间由作者配置“全部正确、任意正确、按顺序”等通用多目标聚合规则。
- 把编辑器图层组作为运行时容器。
- 同一事件为同一目标覆盖另一份答案。

## 七、v1.2.0 已确认扩展

以下能力已完成产品对齐，但尚未实施。完整规则见 [v1.2.0 需求基线](./roadmap/v1.2.0-requirements.md)。

### 输入答案与算式关系

[Issue #72](https://github.com/RexYoung000/editor/issues/72) 为普通输入框和分数输入框增加多候选正确答案，并允许同一个答题判定容器内的两个输入框建立一条算式关系。`KlInputBox` 默认承担答题判定；普通 `ContainerBox` 只有显式开启“启用答题判定”后才承担同样职责。单框候选答案之间取 OR；容器内未关联空位与所有算式关系之间取 AND。它不改变“一个判定事件只引用一个判定目标”的长期边界，也不跨答题判定容器聚合。

普通答案可以用逗号、分号或回车录入多个候选，分数答案通过可视化编辑器逐个管理。算式关系保存在父级答题判定容器的编辑器专用 `_inputRelations` 属性中，通过输入控件 ID 绑定两个操作数；一个输入框最多参与一条关系。第一版支持加、减、乘、除和相等，加减乘除配置目标结果，例如 `A × B = 4`。允许小数时所有满足输入能力和数学关系的结果都应正确，不需要枚举完整答案组合。

选中输入框时直接编辑自己的候选答案或它参与的关系，选中父容器时查看全部关系和未关联空位状态。输入框只归属最近的答题判定容器，嵌套容器不重复收集，也不能跨容器建立关系。`ContainerBox` 关闭开关时保留配置但按普通布局容器处理，容器内输入框恢复独立判定。删除、改名、排序和复制页面时必须保持稳定引用；失效引用、重复占用、无效结果或空位没有判定规则时阻止预览与发布。历史 `_judgeAnswer` 与 `KlInputBox.answer` 保持读取兼容；启用新规则后，导出运行时在父容器实例上覆盖统一 `isRight()` / `isNull()`，使点击判定、快捷确认和作业自动判定共用结果。

快捷确定按钮面向 `KlInputBox` 时继续兼容 SDK 的 `GameUtils.initConfirm`；面向启用答题判定的 `ContainerBox` 时生成独立的通用点击监听，先区分未完成，再判断正确或错误，并执行默认反馈与可选锁屏。普通 `ContainerBox` 不调用 `getWrongIdx()`、`showHook()` 等 `KlInputBox` 专用能力。

### 选择题答案配置

[Issue #76](https://github.com/RexYoung000/editor/issues/76) 继续把 `ChoiceBox` 作为单个判定目标，但不保存手动题型开关。容器通过稳定元素 ID 保存直属选项中的正确答案：1 个答案自动按单选交互，2 个及以上自动按多选交互；图层名只负责属性面板展示。单选允许点击当前选项取消，多选不限制勾选数量，提交时必须与完整正确答案集合精确一致。

正课与预习由画布内确认按钮触发判定；线上作业和专题测评复用 SDK 右上角完成按钮提交。选项文字点击穿透到下方选项元素。草稿允许临时缺少选项或答案，但预览与发布要求至少两个选项、至少一个有效正确答案。选择题尚未投入老师制作，本期直接切换新版稳定引用，不保留名称答案双轨。

选项反馈遵循“通常底框 → 按压底框 → 黄色选中描边 → 绿/红结果描边”的互斥状态。整题判错时所有已选项显示红色描边，不揭示漏选答案；重新选择时清除结果。正课答对后锁定，答错后允许修改；线上作业继续使用通用“修改 / 完成”和未作答跳过确认。

## 八、验收重点

- 普通按钮、图片和文本都能作为点击判定触发者。
- 独立输入格可以直接设置正确答案并成为判定目标，不要求额外创建 `KlInputBox`。
- 目标选择器只列兼容组件，切换目标后结果分支与答案摘要同步更新。
- 多个触发元素引用同一目标时只使用目标自身的一份答案。
- 目标删除或失效后有明确提示，预览和导出不产生悬空代码。
- 正常课、作业、专题测评和预习的普通事件生成相同监听与动作代码，同一事件不重复绑定；复习课保持纯视频边界。
- 自动测试、浏览器界面和 Electron 真实预览共同覆盖编辑、保存、重新打开、预览和发布结果。
